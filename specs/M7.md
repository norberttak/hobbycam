# M7 – G-code output (`hc-post`, LinuxCNC)

## Scope
**In:** new crate `crates/hc-post`: `PostProcessor` trait, one dialect `LinuxCnc`, `export()` (generate → check → split into **one file
per tool segment** → apply work origin → format), number formatting, comment sanitizing, golden files. `hc-project`: `Machine.tool_change_z`,
project format v3 + v2→v3 migrate. App: File → Export G-code… (Ctrl/Cmd+E), Settings → Machine (safe / clearance / tool change Z), origin
marker at the work origin.
**Out:** other dialects (GRBL, Mach3 …), sanity checks and warnings (M8; `ToolpathNote`s are not written), simulation (M9), tool length
offsets (G43), coolant, `T`/`M6`/`M0` in the output, program date/time, line numbers (N), `%` wrappers, arc linearising, a post-selection UI
(`machine.post` is only read), deleting stale files of an earlier export.

## Decisions (from the user, 2026-10-26)
- **One file per tool segment.** Segment = maximal run of consecutive enabled ops (user order) with the same tool. A tool used again later
  gets a new segment, so user order is kept. Reason: the user re-zeroes Z with the new tool; LinuxCNC may not allow touch-off while a
  program is paused, but always allows it between programs.
- **No `T<n> M6`, no `M0`.** The tool change happens between files, by hand. With hal_manualtoolchange an `M6` would pop a second, useless
  prompt at the start of every file; without a changer config it does nothing. The tool is named in the header comments instead. (No `G43`
  for the same reason: Z is touched off per tool; `G49` in the setup line clears a stale offset from MDI work.)
- **`tool_change_z`**: new machine setting, the Z the file ends at so the bit can be swapped. Default **40 mm** for new projects; the
  v2→v3 migrate sets `max(safe_z, 40)` so a migrated file is always valid. Rule: `tool_change_z ≥ safe_z`, else an export error.

## Public API
```rust
// hc-project
pub struct Machine { pub safe_z: f64, pub clearance_z: f64, pub tool_change_z: f64, pub post: String }
pub const FORMAT_VERSION: u32 = 3;
// migrate: found < 2 as before; found < 3: machine.tool_change_z = max(machine.safe_z, 40.0) when absent
// (machine or safe_z missing → leave it to serde, i.e. a JSON error as for any malformed file).

// hc-post
/// One output file = one tool segment, already checked, in mm, work origin applied. Dialects never see the Project.
#[derive(Debug, Clone, PartialEq)]
pub struct Job { pub name: String, pub index: usize, pub count: usize,     // file index (1-based) of count
                 pub units: Units, pub origin: WorkOrigin, pub safe_z: f64, pub tool_change_z: f64,
                 pub tool: u32, pub tool_name: String, pub ops: Vec<JobOp> }
#[derive(Debug, Clone, PartialEq)]
pub struct JobOp { pub name: String, pub rpm: u32, pub moves: Vec<Move> }
#[derive(Debug, Clone, PartialEq)]
pub struct GcodeFile { pub suffix: String, pub text: String }   // file name = <stem><suffix>.<extension>

pub trait PostProcessor {
    fn extension(&self) -> &'static str;     // without dot; LinuxCnc → "ngc"
    fn program(&self, job: &Job) -> String;  // infallible: export() has checked the job
}
pub struct LinuxCnc;

#[derive(Debug, Clone, PartialEq)]
pub enum PostError {
    UnknownPost(String),                        // "Unknown post processor \"grbl\" (available: linuxcnc)"
    NothingToExport,                            // "Nothing to export: no enabled operations"
    OpFailed { op: String, error: ToolpathError }, // "Operation \"Outline\" has an error: <error>" (first failing op, user order)
    ToolChangeBelowSafe,                        // "Tool change Z must be at or above safe Z"; also non-finite tool_change_z
    BadToolpath(u64),                           // non-finite value or first move not a Rapid (internal bug guard)
}
impl Display for PostError {} impl std::error::Error for PostError {}

/// Trimmed, ASCII case-insensitive: "linuxcnc" → LinuxCnc; anything else (incl. "") → UnknownPost(original string).
pub fn post_for(name: &str) -> Result<Box<dyn PostProcessor>, PostError>;
/// Files in machining order. `name` (the project stem) goes into the headers.
pub fn export(project: &Project, name: &str) -> Result<Vec<GcodeFile>, PostError>;
/// XY of the work zero in drawing coordinates: DrawingOrigin (0,0), StockBottomLeft (min_x, min_y), StockCenter (stock centre).
pub fn work_origin(project: &Project) -> Point;
/// Fixed decimals, then trailing zeros and a trailing '.' removed; "-0" → "0". Never exponent notation.
pub fn fmt_num(v: f64, decimals: usize) -> String;
```
`export` order: `post_for` (unknown post → error even for an empty project); `tool_change_z` check; `generate`; empty → `NothingToExport`;
first `Err` → `OpFailed`; per toolpath: all values finite and first move a `Rapid`, else `BadToolpath(op_id)`; subtract `work_origin` from
every XY (`to`, `at`, arc `center`); split into segments; tool name from `project.tools` (missing → `""`, cannot happen for `Ok`).
**Suffix:** one segment → `""` (so `<stem>.ngc`); otherwise `_<k>_T<n>` with k 1-based and zero-padded to the digit count of N
(N = 12 → `_01_T3`), so files sort in machining order.

## LinuxCNC file (lines end with `\n`, file ends with `\n`, no trailing spaces)
Formatting: values converted with `hc_project::to_display` (mm, or ÷25.4 for inch: coordinates, I/J, R, Q **and feeds**); decimals 3 (mm)
/ 4 (inch) for every value incl. F; RPM integer. **Every G0/G1/G2/G3 line writes X Y Z** (self-contained lines, nothing modal to get wrong,
easy to re-parse; size is irrelevant at hobby scale). **F is modal** within a file: written on G1/G2/G3/G81/G83 only when its formatted value
differs from the last F written in this file (none at file start).
```
(<name> - file <k> of <N>)                         sanitized; also "file 1 of 1"
(Generated by HobbyCAM, LinuxCNC post)             no version/date: goldens stay stable across releases
(Units: mm. Z0 = top of stock. XY0 = drawing origin)   inch / "stock bottom left" / "stock centre" accordingly
(Tool: T<n> <tool name>)
(Op: <op name>)                                    one line per op of the segment
(Before running: load T<n> <tool name> and set Z0 on top of stock)
G17 G21 G40 G49 G80 G90 G91.1 G94 G98              G20 for inch; G91.1 = incremental I/J; G98 for drill returns
G64 P0.01                                          blending tolerance 0.01 mm (inch: P0.0004); plain G64 may round corners a lot
G0 Z<safe>                                         the tool may sit on the stock after touch-off
S<rpm> M3                                          rpm of the first op
G4 P2                                              fixed 2 s spin-up dwell (hobby spindles have no at-speed signal)
per op: (<op name>)
        if its rpm differs from the previous op's in this file: S<rpm> M3 / G4 P2
        <moves>
G0 Z<tool_change_z>
M5
M2
```
Move mapping (current position tracked from the op's first Rapid):
- `Rapid(p)` → `G0 X Y Z`; `Linear{to, feed}` → `G1 X Y Z [F]`.
- `Arc{to, center, ccw, feed}` → `G3` (ccw) / `G2` `X Y Z I J [F]`, I/J = centre − current position (unrounded), then formatted. If the
  formatted end X/Y equal the formatted start X/Y (tiny arc) write `G1 X Y Z [F]`: LinuxCNC would read a full circle.
- `Drill{at, z_bottom, peck, r_plane, feed}` → `G81 X Y Z<z_bottom> R<r_plane> [F]`, `peck: Some(q)` → `G83 X Y Z R Q<q> [F]`. G98 returns to
  the Z before the cycle; tracked position = (at, that Z). `G80` before the first non-Drill move after a Drill and after an op's last move
  if it is a Drill (with Rapids between holes that is after every hole).
- `sanitize_comment(s)`: `(`→`[`, `)`→`]`, control chars → space, non-ASCII → `?`, trimmed, max 60 chars, empty → `-`.

## App
- `AppState::gcode(&mut self) -> Option<Vec<GcodeFile>>`: `export(&project, stem)`, stem = project file stem or `untitled`; `Err` →
  `msg(Error, "Cannot export G-code: <e>")`, `None`.
- `AppState::write_gcode(&mut self, base: &Path, files: &[GcodeFile]) -> bool`: dir + stem from `base` (extension stripped), each file
  `<stem><suffix>.<ext>` via `hc_project::atomic_write`, in order, stop at the first failure. Success: Info `Exported N file(s): a.ngc, b.ngc`.
  Failure: Error `Cannot write c.ngc: <e>. Written: a.ngc, b.ngc` (or `Written: none`). Does not touch `dirty` / `path`.
- `App::export_gcode()`: `gcode()` first (errors shown **without** a dialog), then rfd save dialog (filter "G-code" + `extension()`, default
  name `<stem>.<ext>`, start dir = project dir); the chosen name is the base, then `write_gcode`.
- File menu "Export G-code…" (`SC_EXPORT = COMMAND+E`) after "Import DXF…", also in `shortcuts()`.
- Settings → "Machine" submenu: `length_field` rows "Safe Z", "Clearance Z", "Tool change Z" on a copy of `project.machine`, then
  `AppState::set_machine(m)` (stores, sets `dirty` if changed). No validation in the UI: toolpath/export errors report bad values.
- Canvas: origin arrows drawn at `world_to_screen(work_origin(project))` (one-line change; grid and axes stay at the drawing origin).

## Risks
- Stale files: a re-export with fewer segments leaves e.g. `<stem>_3_T1.ngc` from before; overwritten files leave `.ngc.bak`
  (`atomic_write`). The success message lists exactly the files written. Documented in M11.
- The rfd overwrite prompt only covers the base name; suffixed files are overwritten silently (with `.bak`).
- Each file starts with `G0 Z<safe>` from wherever the user left the tool; if the tool is jogged below the stock top that is a straight up move,
  so it is safe.
- LinuxCNC arc radius tolerance: rounding error ≤ ~0.0015 mm / 0.00015 in, below its limit (from memory, not checked against a live install).
  Tiny arcs → G1.
- The canvas grid/axes still use the drawing origin while the arrows show the work origin; M9 may revisit.

## Architect review of the implementation (2026-10-26)
State: tester reports 381 tests green (22 hc-post edge tests, a structural checker over all goldens), and the two-tool example matches
test 1 byte for byte. The API, the file layout, segmenting, suffixes, migrate v2→v3, the Machine submenu, the origin arrows and
`.gitattributes` all match the spec. No unnecessary code found.

**Rulings**
1. **Must-fix: degenerate tiny arcs.** LinuxCNC's center-format check, as documented in its G-code reference (from memory, not tried on a
   live install), runs on the values as written: r1 = |c − s| and r2 = |c − e|, with s the start, e the end and c = s + (I, J). It fails if
   |r1 − r2| > 0.5 mm / 0.05 in, or if |r1 − r2| > 0.005 mm / 0.0005 in **and** > 0.1 % of the radius. It also rejects a zero radius.
   Our rounding error on |r1 − r2| is at most about 0.0014 mm / 0.00014 in, well below the 0.005 mm / 0.0005 in tolerance, so only the
   small-radius case fails. **Rule:** using the formatted values, write `G1 X Y Z [F]` instead of the arc when the formatted end X/Y equal
   the formatted start X/Y (existing rule), or when min(r1, r2) < 10·10^-d in output units (0.01 mm / 0.001 in). The chord error is
   ≤ r ≤ 0.0254 mm, which is harmless. Tests: the tester's inch case `(0,0)→(0.0001 in,0)`, r ≈ 0.00005 in → `G1`; an mm quarter arc with
   r 0.004 → `G1`; an mm quarter arc with r 0.02 → `G2`/`G3`. The round-trip checker also asserts, for every G2/G3, r1, r2 ≥ 10·10^-d and
   |r1 − r2| ≤ 0.005 mm / 0.0005 in.
2. Undefined behaviour, now defined:
   (a) Accept. Ties use Rust's formatter: half to even on the exact binary value (0.0625 → "0.062", 0.1875 → "0.188"). This is
       deterministic. Add a test pinning those two values.
   (b) Accept. Trim, cut to 60, then trim the end again. This is the intended rule.
   (c) Accept. `;` inside `( … )` is plain text for LinuxCNC.
   (d) Accept. The 1e-9 mm tolerance is now part of the rule: error if tool_change_z < safe_z − 1e-9 or tool_change_z is not finite.
   (e) Accept. Not a post rule. Toolpath invariants (M5 test 10) cover it, and M8 may add a check.
   (f) Accept all three. rpm 0 → `S0 M3` (M8 warns). A job with no ops writes no spindle lines (export never builds one). An empty tool name
       gives `(Tool: T1 -)`, which is cosmetic.
   (g) Accept. A v3 file without `tool_change_z` is a JSON error, like any other missing required field.
3. Coder deviations: accept all. The `.gitignore` exception is needed because `*.ngc` is ignored. Checking BadToolpath after the shift also
   catches a non-finite stock. The message text, the extension in `write_gcode` taken from the post, per-value sanitizing (tool and op names
   are cleaned separately, which is correct), the fixture values and the `stem()` helper are all fine. The reader skipping Z-only `G0` is
   acceptable because the footer is checked separately, but later it should update Z on such lines so a G81 right after one would be checked.
4. **Must-fix, cheap: stale files.** Keep "no auto-delete". After a successful write, list `<dir>` and collect the files named
   `<stem>_*_T*.<ext>` and `<stem>.<ext>` that were not just written. If there are any, add one Warning:
   `Older files from a previous export are still in the folder: a.ngc, b.ngc`. Reason: running an old "file 3 of 3" machines the wrong part,
   and the check is about 10 lines. Test: write 3 segments, then 2 → one Warning naming `out_3_T1.ngc`. The `.bak` files are not listed.
