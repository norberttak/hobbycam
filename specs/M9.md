# M9 – Simulation

## Scope
**In:** new crate `crates/hc-sim` (pure, no egui): turns the `generate` output into a timeline of steps in export order, position at
time t (lines, arcs, drill cycles, Z included), per-file and total time estimate. App: a Simulation panel (play/pause, speed, time
slider, readout, time per file), and on the canvas the travelled feed path as a swept band (width = tool diameter, colour = depth)
plus the animated tool circle.
**Out:** material removal / voxel or heightmap model, 3D view, acceleration and jerk, LinuxCNC G64 blending, collision detection,
gouge detection, a machine rapid-rate setting (see Decisions), simulating ops whose toolpath failed, sound, video export, a
G-code file reader (the sim reads the move list, not `.ngc` text).

## Decisions
- **Rapid rate: fixed constant `hc_sim::DEFAULT_RAPID = 2500.0` mm/min, no project setting, no format bump.** On hobby jobs
  feed moves dominate the time (a pocket is mostly G1/G2/G3), and the missing acceleration makes the estimate low by more than
  the rapid rate can fix. A setting would need format v4, a migrate, fixtures and a menu row. All of that buys only a few percent
  of accuracy. `simulate` takes the rapid rate as a parameter, so a later `Machine.rapid_feed` setting is a one-line change at the
  call site plus the format bump. 2500 mm/min is in the usual range for hobby routers (1000–5000).
- **Order mirrors `hc_post::export`:** enabled ops in user order (the `generate` output). One `Block` per G-code file, which is a
  maximal run of consecutive ops with the same tool. The grouping rule is copied from `export` (about 5 lines). hc-sim does **not**
  depend on hc-post, because export shifts coordinates to the work origin and the canvas needs drawing coordinates. Test 9 pins the
  two together.
- **Tool changes are not timed.** Blocks follow each other with no gap: block k+1 starts at the t1 of block k. At the start of a block
  the tool is placed at the target of its first `Rapid` with no time (the real start position after a manual change is unknown).
  The post header `G0 Z<safe>` and the footer `G0 Z<tool_change_z>` are not simulated (about 1 s per file).
- **Spindle dwell is timed:** `SPINUP_S = 2.0` s (the `G4 P2` of hc-post) at the start of each block and before each op whose rpm
  differs from the previous op in the same block, the same rule as the post. It is a `Dwell` step at the current position.
- **Failed ops are skipped, not fatal.** `Err` entries are listed in `Sim::skipped` and the panel says so. Export refuses those
  projects, but simulating the good ops is still useful while editing.
- **Invalid moves are an error, never infinite time or NaN.** Feed ≤ 0 or non-finite, a non-finite value, peck ≤ 0 or non-finite,
  more than `MAX_PECKS = 10_000` pecks, or a first move that is not a `Rapid` → `Err(SimError::BadMove)`. `generate` already
  rejects zero feed (M8 reports it), so this is a guard for the pure API. The check runs before zero-length moves are dropped, so a
  zero-length move with feed 0 is still an error. A rapid rate that is ≤ 0 or non-finite is a programmer error: `assert!`.
- **Zero-length moves** (3D length < `1e-9` mm; arcs with zero sweep) produce no step.

## Public API (hc-sim)
```rust
/// mm/min; see the M9 Decisions.
pub const DEFAULT_RAPID: f64 = 2500.0;
/// Seconds; the same as hc-post's `G4 P2`.
pub const SPINUP_S: f64 = 2.0;
pub const MAX_PECKS: usize = 10_000;

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum StepKind { Rapid, Feed, Dwell }

#[derive(Debug, Clone, PartialEq)]
pub struct Step {
    pub kind: StepKind,
    pub from: Point3,
    pub to: Point3,
    /// XY arc: centre and signed sweep in rad (+ = ccw, |sweep| <= π). None = straight.
    pub arc: Option<(Point, f64)>,
    /// mm/min: the rapid rate for Rapid, the move feed for Feed, 0 for Dwell.
    pub feed: f64,
    /// Seconds from the start of the whole job.
    pub t0: f64,
    pub t1: f64,
    pub op: u64,
    pub tool: u32,
    pub rpm: u32,
}
impl Step {
    /// Position at absolute time t, clamped to [t0, t1]. Line: lerp. Arc: angle, radius (|from−c| → |to−c|) and Z
    /// all linear in time. `point_at(t1) == to` exactly (return `to`, do not evaluate).
    pub fn point_at(&self, t: f64) -> Point3;
}

/// One G-code file.
#[derive(Debug, Clone, PartialEq)]
pub struct Block { pub tool: u32, pub ops: Vec<u64>, pub t0: f64, pub t1: f64 }

#[derive(Debug, Clone, PartialEq, Default)]
pub struct Sim {
    pub steps: Vec<Step>,
    pub blocks: Vec<Block>,
    /// Ops whose toolpath is an Err (not simulated), in order.
    pub skipped: Vec<u64>,
}

#[derive(Debug, Clone, PartialEq)]
pub enum SimError {
    /// The op id and the index of the move in `Toolpath::moves`.
    BadMove { op: u64, index: usize },
}
// Display: "Cannot simulate operation 3: move 7 is invalid"; impl std::error::Error.

/// `toolpaths` = the output of `hc_toolpath::generate`. Pure and deterministic.
pub fn simulate(toolpaths: &[(u64, Result<Toolpath, ToolpathError>)], rapid: f64) -> Result<Sim, SimError>;

impl Sim {
    /// `blocks.last().t1`, or 0.
    pub fn total(&self) -> f64;
    /// The step active at t: the first step with t1 >= t (binary search, `partition_point`), clamped to the last step;
    /// t <= 0 → 0. None if there are no steps.
    pub fn step_at(&self, t: f64) -> Option<usize>;
    pub fn position_at(&self, t: f64) -> Option<Point3>;
}

/// Rounded to whole seconds: 4.6 → "0:05", 125 → "2:05", 3725 → "1:02:05". Negative / NaN → "0:00".
pub fn fmt_duration(secs: f64) -> String;
```

## Move interpretation
Current position `p`. Duration = length / feed × 60 s. Steps are appended with `t0` = the running clock.
- `Rapid(q)`: a straight Rapid step p → q at `rapid` (LinuxCNC G0 is a coordinated straight line).
- `Linear { to, feed }`: a straight Feed step; length = 3D distance.
- `Arc { to, center, ccw, feed }`: sweep as in `canvas.rs`: ccw `(a1 − a0).rem_euclid(TAU)`, cw `−(a0 − a1).rem_euclid(TAU)`.
  Length = `hypot(r0 · |sweep|, Δz)` with r0 = |p − c|, so a helix works even though `generate` never makes one.
- `Drill { at, z_bottom, peck, r_plane, feed }` (G98, z0 = p.z at the cycle start), expanded to: Rapid to (at, z0) if the XY
  differs; Rapid to Z r_plane; then
  - `None`: Feed to z_bottom;
  - `Some(q)`: n = ceil((r_plane − z_bottom)/q − 1e-9) pecks with bottoms b_k = max(r_plane − k·q, z_bottom). Peck k: Rapid down
    to b_(k−1) (skipped for k = 1, where b_0 = r_plane), Feed to b_k, then a Rapid to r_plane except after the last peck. This is
    LinuxCNC's G83 without its small clearance above the previous bottom.
  - finally a Rapid to Z max(z0, r_plane).
  All feed steps use `feed`. The position afterwards is (at, max(z0, r_plane)).

## App
- `AppState.sim: Result<Sim, SimError>`, rebuilt inside `refresh_toolpaths` (same condition, `simulate(&self.toolpaths,
  DEFAULT_RAPID)`; it is O(moves), so no separate cache). After a rebuild, clamp `sim_view.t` to the new total.
- `AppState.sim_view: SimView { open: bool, playing: bool, t: f64, speed: f64 }`, default closed, paused, t 0, speed 10. Not
  saved in the project.
- `AppState::advance(&mut self, dt: f64)`: when playing, `t += dt.min(0.1) * speed` (a stalled frame does not jump the tool). At
  or past the total: t = total and playing = false. Play at t = total restarts from 0.
- View menu: checkbox `Simulation` (next to "Show toolpaths") toggles `sim_view.open`.
- `panels::sim_panel`: `egui::Panel::bottom("sim")`, shown when open, placed after `status_bar` and before `issues` in `App::show`
  (so it sits directly above the status bar). One horizontal row:
  - button `Play` / `Pause` (the text is the accessible name), button `Restart` (t = 0, keeps the play state);
  - `ComboBox` labelled `Speed` with 1×, 2×, 5×, 10×, 20×, 50×, 100× (the `×` glyph is checked by `ui_glyphs_in_default_fonts`);
  - `Slider` over 0..=total in seconds labelled `Time`, with the value shown by `fmt_duration`. Dragging it pauses playback;
  - a readout label of the current step: `Contour 1 · T1 Flat 3mm · Z -1.500 mm · F 600.000 mm/min · 0:42 / 3:10`. Lengths
    use `fmt_len`, and the feed uses `fmt_len(feed) + "/min"` in project units. A Rapid step shows `Rapid` in place of `F …`, a
    Dwell shows `Spindle start S12000`.

  A second row holds the time per file, `File 1 · T1 · 2:10`, …, then `Total 3:10`, and the hover text (on Total)
  `Estimate: rapids at 2500 mm/min, no acceleration, tool changes not counted`. If `skipped` is non-empty:
  `Not simulated: 1 operation with errors` in the warn colour. If `sim` is an Err: only its Display text in the error colour.
  If there are no steps: `Nothing to simulate`.
- `App::show`: when `sim_view.playing`, call `advance(ui.input(|i| i.stable_dt) as f64)` and `ctx.request_repaint()`.
- Canvas (only when `sim_view.open` and `sim` is Ok with steps), drawn after the stock and before the items, so the item and
  toolpath lines stay visible on top:
  - **Swept band:** every Feed step up to t (the active step only up to `point_at(t)`) whose min Z < −1e-6 (cutting moves). Draw
    it as `Shape::line` (arcs tessellated with `hit::tessellate_arc`), stroke width = tool diameter × zoom (min 1 px), plus a
    `circle_filled` of radius d/2 at each step end, which gives round joins without the miter spikes egui draws at sharp turns.
    The colour is opaque (so overlaps do not darken) and lerps from (255, 210, 80) at Z 0 to (170, 40, 40) at Z = −stock
    thickness, clamped, using the step's min Z. It is the same in light and dark mode.
  - **Tool:** at `position_at(t)`, a circle of the tool radius (stroke 2 px, text colour) and a 6 px cross. Rapid steps show the
    tool but add no band.
- Plain toolpath display (`show_toolpaths`) is unchanged.

## Acceptance tests (`crates/hc-sim/tests/sim.rs` unless noted)
The helper `tp(op, tool, rpm, moves)` builds an `Ok` toolpath. Rapid = 6000 mm/min (100 mm/s) in every test except 13. Times are
asserted within 1e-9 s and positions within 1e-9 mm. Every total includes the 2 s spin-up dwell.
1. **Line:** `Rapid(0,0,5)`, `Linear(0,0,-1) F150`, `Linear(30,40,-1) F600`, `Rapid(30,40,5)` → steps Dwell, Feed, Feed, Rapid (the
   first rapid is the block start, so it gives no step); total = 2 + 2.4 + 5 + 0.06 = 9.46. `position_at(6.9)` = (15, 20, −1);
   `position_at(−1)` = (0,0,5); `position_at(1e9)` = (30,40,5); `step_at(1.0)` is the Dwell.
2. **Arc ccw:** `Rapid(10,0,5)`, `Linear(10,0,-1) F600`, `Arc → (0,10,-1) c(0,0) ccw F600` → arc duration 5π/10 s; at the arc's
   mid-time the position is (7.0711, 7.0711, −1) (within 1e-4); `point_at(t1)` == to exactly.
3. **Arc cw:** the same start, `Arc → (0,-10,-1) cw` → mid (7.0711, −7.0711, −1).
4. **Semicircle (sweep = π):** (10,0) → (−10,0) about (0,0): ccw mid (0, 10), cw mid (0, −10). Duration 10π/10 s.
5. **Helix:** an arc as in 2 with to.z = −2 → length hypot(5π, 1), Z at mid-time −1.5.
6. **Drill plain:** `Rapid(0,0,5)`, `Drill{at (0,0), z_bottom −5, peck None, r_plane 2, F100}` → steps Dwell, Rapid (to Z 2),
   Feed (to −5), Rapid (to 5); total = 2 + 0.03 + 4.2 + 0.1 = 6.33; position at the end (0,0,5).
7. **Drill peck:** the same with peck 3 → peck bottoms −1, −4, −5; feed length 7 (4.2 s); rapid length 3+3+3+6+6+10 = 31 (0.31 s);
   total 6.51. Peck 1e-9 → `BadMove { op, index: 1 }` (more than MAX_PECKS). Peck 0 → BadMove.
8. **Drill XY move:** Rapid to (0,0,5), then Drill at (10,0) → first a Rapid step (0,0,5) → (10,0,5), 0.1 s.
9. **Blocks = export files:** ops T1, T1, T2, T1 → 3 blocks with tools [1, 2, 1] and ops [[a, b], [c], [d]];
   `blocks[k+1].t0 == blocks[k].t1`; `blocks[0].t0 == 0`; `total == blocks.last().t1`. The sum of the block durations equals the
   sum of the step durations (no time for tool changes). Cross-check against hc-post (app test, because the app already depends
   on both crates): the test 15 Bracket project with ops T1 Outside, T2 Drill, T1 Pocket → `sim.blocks.len() == 3 ==
   hc_post::export(..).len()`, and the block tools are in file order.
10. **Spin-up:** two T1 ops with rpm 10000 then 12000 → 2 Dwell steps (4 s); with equal rpm → 1. The second op's first Rapid is
    timed from the end of the first op (not a teleport); after a tool change the next block's first Rapid is a teleport.
11. **Edge cases:** `simulate(&[])` → `Sim::default()`, total 0, `step_at`/`position_at` None. All entries Err → no steps, `skipped`
    = their ids in order. One Err between two Ok T1 ops → it is skipped, and the Ok ops still form **one** block (export would
    refuse; the sim simply leaves it out). Zero-length Linear, Rapid and zero-sweep Arc → no step, and the total is unchanged. A
    toolpath of only `Rapid` → one block with just the Dwell.
12. **Bad input:** Linear feed 0 / −1 / NaN → `BadMove { op, index }` with the right index; a zero-length Linear with feed 0 →
    BadMove; a NaN coordinate → BadMove; first move Linear → `BadMove { index: 0 }`; Display text as in the API.
13. `simulate(.., DEFAULT_RAPID)` on test 1 → rapid step 6 mm = 0.144 s. `simulate(.., 0.0)` panics (`#[should_panic]`).
14. `fmt_duration`: 0 → "0:00", 4.4 → "0:04", 4.6 → "0:05", 59.5 → "1:00", 125 → "2:05", 3600 → "1:00:00", 3725 → "1:02:05",
    −3 → "0:00", NaN → "0:00".
15. **Monotonic** (property-style loop over the Bracket toolpaths of the M8 test 28 fixture, app test): t0 ≤ t1, each step's t0 ==
    the previous t1, `point_at(t0) == from` within 1e-9, each step's `from` == the previous `to` except at block starts, and every
    value is finite. The Bracket total is > 0 and below 10 h.
16. **App state:** `refresh_toolpaths` fills `sim`; `advance(0.5)` while paused leaves t unchanged; while playing at speed 10,
    `advance(0.05)` adds 0.5 s and `advance(10.0)` adds only 0.1 × speed = 1 s; advancing past the total stops at the total and pauses; play at the end restarts
    at 0; changing an op so the total gets shorter clamps t.
17. **Kittest** (non-ignored, `main.rs` tests): Bracket with an Outside op → View → `Simulation` opens the panel; `Play`, `Restart`,
    `Speed` and `Time` exist; clicking `Play` sets `playing` and shows `Pause`; a label starting with `Total ` exists, and so does
    a label `File 1 · T1 · …`. Setting `sim_view.t` to the middle of the first Feed step with `from.z < 0` and running a frame shows a readout
    containing `Z -` and `mm/min`. A project with an Inside op that fails (tool too large) shows `Not simulated: 1 operation with
    errors`.
18. **Shot** (`#[ignore]`) `shot_sim`: the M5 `shot_toolpaths` project without the failing op, panel open, t at 60 % of the total,
    → `sim.png` and `sim_light.png`. Manual check: the swept band is as wide as the tool, depth colours are visible (pocket
    lighter than the through contour), the tool circle is at the readout's position, there is no tofu, and the panel fits at
    1280 px.

## Risks
- **The estimate is low** without acceleration, especially on pockets with many short segments and on G64 corners. The hover text
  says so; M11 documents it ("expect the real time to be 10–30 % longer"). This is acceptable for hobby planning.
- **The rapid rate may not match the user's machine** (LinuxCNC `MAX_VELOCITY`). It is easy to upgrade (see Decisions).
- **Paint cost:** a big pocket gives thousands of wide strokes plus circles per frame while playing. It is fine at DXF scale. If it
  lags: shortcut, cache the screen points for the completed steps and only extend them.
- **Wide strokes in egui:** polyline joins on thick lines can spike at sharp angles. Drawing per step with round caps avoids
  most of that, but very short tessellated arcs at high zoom may still show small artefacts. This is only cosmetic.
- Drill-cycle expansion follows the LinuxCNC docs from memory (G98, pecks from R, retract to R between pecks). A small
  difference in timing is harmless.
- Keep the grouping in `simulate` in step with `hc_post::export` if export changes. Test 9 catches a drift.

## Architect review of the implementation (2026-10-27)
State: 518 pass, 6 ignored (5 shots + 1 bug test). The API, move interpretation, block grouping, dwell rule, panel, canvas band and
tool marker match the spec. No spec items are missing.

**Coder deviations**
1. dt clamp vs test 16: **accept the clamp**. The spec text was wrong (0.5 s exceeds the 0.1 s clamp); test 16 is corrected above.
2. Test 17 readout on the first Feed step with `from.z < 0`: **accept**. The first Feed is the plunge from clearance Z, whose
   midpoint is above Z 0. Test 17 is corrected above.
3. Slider and its value field both named `Time`: **accept**. That is how egui's Slider exposes itself; asserting 2 nodes is fine.
4. `shot_sim` with the contour at full stock thickness and the pocket first: **accept**. It makes the depth colours comparable.
5. Zero-sweep arc with a Z change: **change**. The post writes such an arc as `G1` (M7 ruling 1), so the machine moves in Z. Treat it
   as a straight Feed step (`arc: None`, length = 3D distance). With no Z change it stays a zero-length move (no step).

**Tester findings**
A. Infinite time from finite extreme input: **must-fix**. After each move, a non-finite clock → `BadMove { op, index }` of that move.
   Lengths use `hypot` (no `powi` overflow). The ignored test is enabled.
B. `position_at(NaN)`: **accept**. NaN time is unspecified; the app never passes it.
C. Drill with z0 below R: **fix, cheap**. Match LinuxCNC: if z0 < r_plane, rapid to Z r_plane first, then XY. The return Z stays
   max(z0, r_plane). Add a test (start Z 1, R 2: the first step is a Z rapid at the start XY). This is unreachable from `generate`.

**Other finding**
D. Closing the panel while playing keeps advancing and repainting every frame (CPU drain on an invisible animation). **Must-fix**:
   closing the panel pauses (`playing = false` when `open` is false). Add an assert to test 17: uncheck `Simulation` while playing,
   and `playing` is false.
